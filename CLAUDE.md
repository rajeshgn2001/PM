# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Read `AGENTS.md` first: it holds the business requirements, technical decisions, color scheme, and coding standards (keep it simple, no over-engineering, no emojis, prove root cause before fixing). Planning and progress live in `docs/PLAN.md`; the DB schema is in `docs/DATABASE.md`. Subdirectories have their own `AGENTS.md` (`frontend/`, `backend/`, `scripts/`). The latest code review and its status are in `docs/code_review.md`.

## Commands

Full app (Docker, serves on http://localhost:8000, sign in as `user` / `password` or create an account):
- `./scripts/start.sh` / `./scripts/stop.sh` (wraps `docker compose up -d --build` / `docker compose down`; Windows equivalents are `.bat` and `.ps1`). The board persists in the `kanban-data` volume; `docker compose down -v` resets it.

Backend (`backend/`, Python 3.12, uv; dependencies locked in `uv.lock`, test tools in the `dev` group, which the image excludes):
- Tests in a throwaway container (uv is not installed on the host): `docker run --rm --env-file .env --entrypoint uv pm-app run --frozen pytest -q` (build the image first; `--env-file` enables the live Claude test)
- Against the working tree without rebuilding: `docker run --rm -v "$PWD/backend":/w -w /w -e UV_PROJECT_ENVIRONMENT=/tmp/venv --env-file .env --entrypoint uv pm-app run --frozen pytest -q -p no:cacheprovider --cov=.`
- Single test: append e.g. `tests/test_board.py::test_create_board`
- After changing dependencies: `docker run --rm -v "$PWD/backend":/w -w /w --entrypoint uv pm-app lock`

Frontend (`frontend/`):
- `npm run test` (Vitest unit tests), `npm run test:coverage`, single file: `npx vitest run src/components/KanbanBoard.test.tsx`, single test: add `-t "<name>"`
- `npm run test:e2e` (Playwright; needs a running app, default `http://127.0.0.1:8000`). E2E tests register accounts and edit the demo board, so run them against a throwaway container to keep the real board clean: `docker run -d --rm --name kanban-e2e -p 8001:8000 --env-file .env pm-app`, then `PLAYWRIGHT_BASE_URL=http://127.0.0.1:8001 npm run test:e2e`, then `docker stop kanban-e2e`. The drag test assumes seed data.
- `npm run lint`, `npm run build` (static export to `frontend/out`)

## Architecture

Single container, single origin. The Dockerfile builds the Next.js app as a static export (`output: "export"`) and copies `frontend/out` into `backend/static/`, which FastAPI mounts at `/` after all `/api/*` routes. The committed `backend/static/index.html` is only a scaffolding placeholder; the real UI exists only in the Docker image (or after manually building and copying `frontend/out`). The frontend calls relative `/api/...` URLs and there is no dev proxy, so `npm run dev` alone has no working backend.

Board data model is shared across layers and must stay in sync: `frontend/src/lib/kanban.ts` (TS types), `backend/models.py` (Pydantic `BoardData`), and the JSON stored in the `boards.data` column. Shape: `columns` is an ordered list of `{id, title, cardIds}`, `cards` is a map of id -> `{id, title, details, priority, dueDate, assignee, labels, checklist}` (`priority` is `low`/`medium`/`high` or null, `dueDate` is `YYYY-MM-DD` or null, `assignee` is a board member's username or null, `labels` is a list of strings, `checklist` is a list of `{id, text, done}`). Column order and card order come from `columns[].cardIds`.

Persistence: `backend/database.py` uses raw `sqlite3` (tables `users`, `boards`, `sessions`, `board_members`, `board_groups`, `board_placements`). `init_db()` runs in the FastAPI lifespan, creates missing tables, adds `boards.version` to older databases, gives users without a group a `DEFAULT` group, rehashes any legacy plaintext passwords, and seeds the `user` account plus the default 5-column/8-card board. Board access (owner or member) is checked in `get_board` / `list_boards` via the `ACCESSIBLE_BOARDS` query; the other board functions act on an already-checked board. DB path is `backend/kanban.db` unless `DB_PATH` is set; Docker sets `/data/kanban.db` on the `kanban-data` volume, and `backend/tests/conftest.py` gives each test its own temp DB. The frontend saves the whole board via `PUT /api/boards/{id}` with `{version, data}` (debounced 150ms, and chained so each save sends the version the previous one returned) after every mutation; there is no per-card API. Each save bumps `boards.version`; a save at a stale version returns 409, and the client reloads the board and shows a notice instead of overwriting. Other failures show "Sync error". Saves also reject (422) an assignee who is not a board member; removing a member or deleting an account unassigns that user's cards. Shared boards (more than one member) poll every 10s while idle (no open card dialog, no AI request, nothing unsaved). `BoardData` has a validator enforcing at least one column, unique column IDs, and that every card is in exactly one column, so any write that breaks this is rejected. The frontend renders nothing until the board has loaded (no demo fallback), and the board is `inert` while an AI request is in flight so AI replies cannot overwrite concurrent edits.

Auth: passwords are hashed with scrypt (stdlib `hashlib`). Login and register return a random session token stored in the `sessions` table; the frontend keeps it in sessionStorage (closing the tab signs out) and sends it as `Authorization: Bearer`. Every endpoint except health, login and register requires it (`current_user` dependency in `main.py`); a board the caller cannot access returns 404, and owner-only actions (rename, delete, invite, remove others) return 403 for members. Logout deletes the session, a password change revokes the user's other sessions, and deleting the account cascades to boards and sessions. On any 401 the frontend clears the session and returns to sign in (`AUTH_EXPIRED_EVENT`).

Board groups are personal, including for shared boards. A user's oldest group is their default and holds every board with no `board_placements` row, so renaming it changes nothing else and existing boards need no migration. Moving a board (`PUT /api/boards/{id}/group`) does not touch `boards.data` or `boards.version`.

Frontend structure: `page.tsx` gates on auth, `Workspace` holds the board list sidebar (grouped through `BoardGroupSection`, with its own `DndContext` for moving boards) and account dialog, and renders `KanbanBoard key={boardId}` (which owns `CardDialog` for editing and `ShareDialog` for members) so switching boards remounts it (fresh state and chat history).

AI: `POST /api/boards/{id}/ai/chat` in `main.py` builds a system prompt containing that board's JSON, its member list, the current username and today's date and asks the model for `{message, board_update}`. If `board_update` is present it is validated against `BoardData` and the member list and saved at the version the AI saw (409 if someone saved meanwhile); the response carries the new `version`; an invalid update (or any AI failure, including the 120s timeout) returns 500 with a readable `detail`, which the sidebar shows, and the DB is untouched. The frontend replaces its board state with the returned `board_update`. `backend/ai.py` shells out to the Claude Code CLI (`claude -p --output-format json --tools "" --json-schema ...`), which the Dockerfile installs; it authenticates with the user's Claude subscription via `CLAUDE_CODE_OAUTH_TOKEN` in `.env` (an `ANTHROPIC_API_KEY` in the environment would take precedence, so keep it out). Chat history is flattened into the prompt text, and the reply's `structured_output` is validated against `ChatOutput`. Backend AI chat tests stub `ai.run_claude` (so `ChatOutput` validation still runs); the `/api/ai/test` test stubs `main.generate_simple_completion`; the live connectivity test is skipped when the `claude` CLI is not installed.
